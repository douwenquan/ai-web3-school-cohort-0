## 一、核心问题回答

### Q1：Agent 参与 DeFi 操作时，真正执行的是什么链上动作？

Agent 不在"发交易"，而是在做一系列**结构化的链上调用**。以 DCA Agent 的 swap 为例：

```
Agent 的执行链路（非技术层面）：
  理解意图 → 构造参数 → 检查边界 → 发起调用 → 等待确认 → 验证结果 → 记录日志

Agent 触发的链上动作（技术层面）：
  eth_call（只读报价）→ eth_sendRawTransaction（签名交易上链）
```

一次 swap 在链上真正发生的事情：

| Agent 做的 | 链上实际发生的 | 谁签名 | 谁付 Gas |
|-----------|--------------|--------|---------|
| 调用 `dex.quote` | 对 Uniswap Quoter 合约发起 `eth_call`（只读） | 不需要签名 | Agent 执行环境 |
| 调用 `swap.execute` | 构造 swap 交易数据 → Cobo Policy Engine 检查 → MPC 签名 → `eth_sendRawTransaction` 上链 | Cobo MPC | Cobo 钱包中的 ETH |

关键认知：**Agent 从来不在链上"被看到"**。链上只有两个地址：
- 用户的 Cobo 托管钱包（Sender）
- Uniswap V3 Router（Target Contract）

Agent 是**离线的编排层**，链上看到的所有交易都来自 Cobo 托管钱包。

### Q2：如何限制 Agent 的预算、协议、Token、合约、时间窗口和最大损失？

详见 Module D（权限策略设计），这里摘要核心原则：

| 限制维度 | 实现方式 | DCA 场景中的值 |
|---------|---------|--------------|
| **预算（Budget）** | Pact Policies：累计上限 | 累计 ≤3,000 USDC |
| **协议（Protocol）** | 合约白名单 | 仅 Uniswap V3 Router |
| **Token** | Token 白名单 | 仅 USDC → ETH |
| **合约（Contract）** | 合约地址 allowlist | Uniswap V3 Router + x402 收款地址 |
| **时间窗口（Time Window）** | Pact Completion Conditions | 最长 30 天 |
| **最大损失（Max Loss）** | 单笔限额 + 滑点上限 | 单笔 ≤200 USDC, 滑点 ≤1% |

**最大损失的计算公式：**

```
最大损失 = max(单笔损失) × 最大执行次数
单笔损失 = (swap 金额 + 滑点损失 + Gas 费) × 是否可回退（不可回退 = 1, 可回退 = 0）

DCA 场景：最大损失 = 200 USDC × (累计预算 / 单笔金额) + Gas 费
                 = 200 × (3000/100) + ≈0.5 ETH Gas
Agent 最大损失的资产 = 累计预算上限（3,000 USDC）+ 少量 ETH Gas
```

### Q3：Swap、Approve、Deposit、Borrow、Withdraw、Redeem 等动作分别有什么风险？

#### 风险矩阵总览

| 操作 | 风险等级 | 主要风险 | 是否可回退 | DCA Agent 涉及 |
|------|---------|---------|-----------|---------------|
| **Swap** | L2 | 滑点损失、MEV 抢跑、交易 revert | ⚠️ 不可回退（成交即终局） | ✅ 核心操作 |
| **Approve** | L3 | 无限授权、钓鱼合约、授权后被盗 | ❌ 不可回退（除非取消授权） | ⬜ 未涉及（Cobo 管理） |
| **Deposit** | L2 | 合约风险、脱锚、锁定期 | ⚠️ 部分可回退（需等待赎回） | ⬜ 未来扩展 |
| **Borrow** | L3 | 清算风险、健康因子下降、利率波动 | ⚠️ 可部分回退（还款后恢复） | ⬜ 未来扩展 |
| **Withdraw** | L1 | 合约漏洞、提取延迟 | ✅ 可回退（资金到账即完成） | ⬜ 未来扩展 |
| **Redeem** | L2 | 脱锚损失、流动性不足、赎回延迟 | ⚠️ 部分协议有锁定期 | ⬜ 未来扩展 |

#### 各操作详解

##### Swap（交换）

**做什么：** 将一种 token 兑换为另一种（USDC → ETH）

**风险拆解：**

| 风险 | 触发条件 | 后果 | 缓解措施（在 DCA Agent 中） |
|------|---------|------|--------------------------|
| **滑点损失** | 执行时价格波动超出滑点容忍度 | 收到比预期少的 token | 设置合理滑点上限（≤1%），交易前模拟执行 |
| **MEV 抢跑** | 三明治攻击：攻击者看到待处理交易后抢跑 | Agent 以更差的价格成交 | 使用私有 mempool / 设置滑点保护 |
| **交易 revert** | Gas 不足 / 价格影响超限 / 流动性不足 | swap 失败，Gas 已消耗 | 使用 `estimate_contract_call_fee` 预估算 Gas |
| **路径退化** | 报价路径不是最优 | 比预期多付 0.5-3% | 使用 Uniswap V3 的自动路由（Auto Router） |
| **合约漏洞** | Uniswap Router 合约被攻击 | 资金损失 | 合约白名单机制——仅限于已知安全版本 |

**在 DCA Agent 中的体现：**
- Agent 每次 swap 前调用 Quoter 获取报价 → 将价格信息记录到日志
- 执行后调用 `get_transaction_record` 验证实际输出量 → 与报价对比
- 如果实际输出偏离报价超过阈值 → Agent 标记异常并通知人类

##### Approve（授权）

**做什么：** 允许某个合约（如 Uniswap Router）从你的钱包中转移指定 token

**风险拆解：**

| 风险 | 说明 |
|------|------|
| **无限授权** | approve(uint256 max) 让合约可以转走所有余额 |
| **钓鱼合约** | 授权给恶意合约后，资金可被任意转移 |
| **授权残留** | 使用完后未取消授权，后续合约漏洞可能导致资金被盗 |

**在 DCA Agent 中的体现：**
- DCA Agent **不直接执行 approve**
- approve 由 Cobo 钱包在用户层面管理
- Agent 只在 Pact 边界内调 `contract_call`，approve 的状态由 Pact 的 Policies 保护

##### Deposit（存入）

**做什么：** 向协议存入资产以获取收益或作为抵押品（如 Aave 存款、Lido 质押）

**风险拆解：**

| 风险 | 说明 |
|------|------|
| **合约风险** | 存款合约被攻击 → 存款损失 |
| **脱锚风险** | stETH/ETH 脱锚 → 存款价值下降 |
| **锁定期** | 部分协议有锁定期，期间无法提取 |
| **收益波动** | 存款利率变化 → 实际收益低于预期 |

##### Borrow（借贷）

**做什么：** 以存入资产为抵押借出另一种资产

**风险拆解：**

| 风险 | 说明 |
|------|------|
| **清算风险** | 抵押品价值下跌 → 健康因子 < 1 → 被清算 |
| **Oracle 风险** | 价格预言机被操纵 → 错误清算 |
| **利率波动** | 借款利率飙升 → 偿还成本增加 |
| **循环借贷** | 多次借贷循环放大风险 |

##### Withdraw（提取）

**做什么：** 从协议中提取已存入的资产

**风险拆解：**

| 风险 | 说明 |
|------|------|
| **提取延迟** | 部分协议有提取队列（如 Lido 的 stETH → ETH 兑换） |
| **滑点损失** | 提取时流动性不足 |
| **合约异常** | 提取函数被暂停或异常 |

##### Redeem（赎回）

**做什么：** 将流动性质押/存款凭证换回底层资产

**风险拆解：**

| 风险 | 说明 |
|------|------|
| **脱锚损失** | 凭证价格偏离底层资产（如 stETH 折价） |
| **流动性不足** | 兑换池深度不够 → 大额赎回价格不利 |
| **锁定期** | 部分协议要求等待期（如 Lido 的 request → claim 流程） |

### Q4：哪些动作可以在 Pact / Policy 范围内自动执行？哪些必须暂停？

| 操作类型 | 在 Pact 边界内 | 可自动执行 | 需人工确认 | 在 DCA Agent 中 |
|---------|--------------|----------|----------|----------------|
| **Swap（报价 + 执行）** | 金额 ≤ 单笔限额 & 合约在白名单 | ✅ | — | 核心自动执行能力 |
| **x402 支付** | 金额在 Pact 预算内 & 收款地址在白名单 | ✅ | — | 自动付款 |
| **Approval** | 需要更新 token 授权 | — | ❌ | Cobo 层面管理，Agent 不涉及 |
| **Deposit** | （未来扩展） | ⚠️ 需额外 Pact | ❌ 需人类审核 | 未实现 |
| **Borrow** | （未来扩展） | ❌ 风险过高 | ❌ 必须人工确认 | 未实现 |
| **Withdraw** | 提取到指定地址 | ✅（若在 Pact 内） | — | 未实现 |
| **Redeem** | 赎回凭证 | ⚠️ 需检查脱锚风险 | ⚠️ 大额需人工 | 未实现 |
| **Pact 更新** | 修改预算/策略/合约列表 | — | ❌ 必须人类审核 | 核心安全边界 |
| **紧急撤销** | 暂停或终止所有操作 | — | ❌ 人类手动操作 | Freeze / Revoke |

**设计原则：**

```
可自动执行的条件（全部满足）：
  ├─ 1. 操作类型在 Pact 定义的 allowed_operations 中
  ├─ 2. 目标合约在 Pact 的 contract_allowlist 中
  ├─ 3. 交易金额 ≤ 单笔限额
  ├─ 4. 累计金额 ≤ 累计预算
  ├─ 5. 操作时间在 Pact 的有效期内
  └─ 6. 失败次数未超过阈值

需要人工确认的条件（任一满足）：
  ├─ 1. 操作类型不在 Pact 中
  ├─ 2. 合约不在 allowlist 中
  ├─ 3. 金额超限
  ├─ 4. 累计预算已耗尽
  ├─ 5. Pact 已过期
  ├─ 6. 连续失败超过阈值
  └─ 7. 操作涉及高风险动作（borrow、更新权限等）
```

### Q5：执行完成后，如何通过 Tx Record 和 Audit Log 验证、复盘和追责？

#### 验证链路

```
① Cobo API：get_transaction_record_by_request_id
   └─ 获取：tx hash、status、实际输出量、Gas 消耗
   └─ Agent 自动调用，记录到日志

② 区块浏览器验证（人类）
   └─ 根据 tx hash 在 Etherscan / Basescan 上查看
   └─ 验证：Sender 地址、Target 合约、金额、事件日志

③ Cobo 审计日志
   └─ 获取：谁调了什么接口、花了多少钱、被拒绝还是通过、时间戳
   └─ 通过 Cobo App 或 API（get_audit_logs）查看

④ Agent 操作日志
   └─ Agent 本地记录的：执行计划、报价结果、错误分析、决策理由
```

#### 复盘流程

```
执行完成后：

Step 1：Agent 自动比对
  ├─ 预期输出 vs 实际输出 → 差值是否在可接受范围内？
  ├─ Gas 消耗是否异常？
  └─ 是否有异常事件（revert、超时、重试）？

Step 2：Agent 生成执行摘要
  ├─ 本次花费：金额 + Gas
  ├─ 累计花费：已用 / 总预算
  ├─ 执行状态：成功 / 失败 / 部分成功
  └─ 异常列表

Step 3：人类验收
  ├─ 查看执行摘要
  ├─ 打开区块浏览器验证 tx hash
  └─ 确认 → 或 标记异常 → 调查原因

Step 4：Pact 到期后完整回顾
  ├─ 总执行次数
  ├─ 总花费
  ├─ 成功率
  ├─ 平均执行成本
  └─ 失败原因分布
```

#### 责任归属

| 场景 | 证据来源 | 责任归属 |
|------|---------|---------|
| Agent 按 Pact 执行但市场亏损 | tx record 显示按参数执行 | 市场波动，Agent 无责 |
| Agent 执行了超出 Pact 的动作（不应发生） | 审计日志显示越权操作 | 架构故障 → 需检查 Policy Engine |
| Agent 执行失败未通知人类 | Agent 日志中无失败记录 | Agent 缺陷 → 需修复通知机制 |
| 人类批准了不合理的 Pact | Pact 审核记录 | 人类审核失误 |
| Cobo 基础设施故障导致交易失败 | Cobo 审计日志 | Cobo 基础设施责任 |
| 链拥堵导致交易 pending | tx record 状态为 pending | 链网络问题，Agent 可通过 RBF 加速 |

## 二、典型协议详解

### 1. Uniswap V3 — 集中流动性 DEX

#### 是什么

Uniswap V3 是以太坊上最广泛使用的**自动化做市商（AMM）**协议。V3 的核心创新是**集中流动性**——LP 可以在特定价格区间内提供流动性，提高资金效率。

#### Agent 与 Uniswap 的交互

```
┌──────────────────────────────────────────────────────────────┐
│                  DCA Agent × Uniswap V3                        │
├──────────────────────────────────────────────────────────────┤
│                                                               │
│  只读交互（无需签名，无风险）：                                 │
│  ┌──────────────────────────────────────────────────┐        │
│  │  eth_call → Uniswap V3 Quoter                    │        │
│  │  ├─ quoteExactInputSingle(amountIn, tokenIn,     │        │
│  │  │                      tokenOut, fee)           │        │
│  │  └─ 返回：amountOut, sqrtPriceX96, gasEstimate   │        │
│  └──────────────────────────────────────────────────┘        │
│                                                               │
│  写交互（需 MPC 签名 + Gas）：                                 │
│  ┌──────────────────────────────────────────────────┐        │
│  │  Cobo contract_call → Uniswap V3 Router          │        │
│  │  ├─ exactInputSingle(ExactInputSingleParams)     │        │
│  │  │    params: {tokenIn, tokenOut, fee,           │        │
│  │  │             recipient, deadline, amountIn,    │        │
│  │  │             amountOutMinimum, sqrtPriceLimitX96}        │
│  │  └─ 返回：amountOut（实际输出量）                 │        │
│  └──────────────────────────────────────────────────┘        │
│                                                               │
└──────────────────────────────────────────────────────────────┘
```

#### 关键概念

| 概念 | 说明 | Agent 如何处理 |
|------|------|---------------|
| **Slippage（滑点）** | 执行价格与报价之间的偏差 | Agent 在执行前设置 `amountOutMinimum = 报价 × (1 - 滑点%)` |
| **Fee Tier（费率）** | 0.01% / 0.05% / 0.30% / 1.00%，不同费率对应不同波动性池 | Agent 自动选择流动性最深的池 |
| **TWAP（时间加权平均价格）** | Uniswap V3 内置的链上价格预言机 | 可用于报价验证——比较 Quoter 报价 vs TWAP |
| **MEV（最大可提取价值）** | 矿工/验证者通过重排序交易提取的价值 | 三明治攻击：攻击者抢跑买推高价格 → Agent 买在高点 → 攻击者卖 |
| **Allowance（授权额度）** | 用户授权 Router 转移 token 的额度 | DCA Agent 不直接处理，由 Cobo 钱包管理 |
| **交易前模拟** | 在执行前用 `eth_call` 模拟交易结果 | Agent 每次 swap 前模拟——验证不会 revert |

#### Slippage 保护机制

```
Agent 构造 swap 参数时的滑点计算：

① Quoter 返回预期输出量：100 USDC → 0.05 ETH
② Agent 设置滑点上限：1%
③ amountOutMinimum = 0.05 × (1 - 0.01) = 0.0495 ETH
④ 如果执行时实际输出 < 0.0495 ETH → 交易 revert（保护生效）

滑点设置原则：
  ├─ 正常市场：0.5-1%（平衡安全和成交概率）
  ├─ 高波动市场：2-3%（提高成交概率，但接受更高损失）
  └─ Agent 不能自动超限——超过 Pact 约定的滑点上限需要人类批准
```

#### 在 DCA Agent 中的集成

DCA Agent 的 swap 流程已经覆盖了 Uniswap V3 的全部交互，Module D 的权限策略覆盖了合约白名单、金额限制和人工确认阈值。

### 2. Balancer — 加权池 DEX

#### 是什么

Balancer 是另一种 AMM 协议，核心特点是**加权池**——一个池中可以有最多 8 种 token，各 token 有不同权重。与 Uniswap 的 50/50 恒定乘积不同，Balancer 支持 80/20、60/20/20 等权重配置。

#### 与 Uniswap 的核心区别

| 维度 | Uniswap V3 | Balancer V3 |
|------|-----------|-------------|
| **做市模型** | 集中流动性（价格区间） | 加权池（多 token 比例） |
| **池类型** | 每个池 2 种 token | 每个池 2-8 种 token |
| **流动性效率** | 高（集中流动性能将资金集中在活跃交易区间） | 中（全区间分布） |
| **自定义权重** | 固定 50/50 | 80/20、60/20/20 等 |
| **费用层级** | 0.01%/0.05%/0.30%/1.00% | 可自定义 |
| **适用场景** | 主流币对交易 | 指数池、多资产组合、加权策略 |
| **路由** | Uniswap X（跨池自动路由） | Balancer SOR（Smart Order Router） |

#### Agent 如何与 Balancer 交互

与 Uniswap 类似，Agent 通过：
1. **只读**：Balancer SOR 查询最优路径 + 报价
2. **写**：`swapExactTokensForTokens` 或 `batchSwap`（多步交换）

#### 为什么 DCA Agent 可能用到 Balancer

如果 DCA 策略不是简单的 USDC → ETH，而是构建一个加权组合（如 60% ETH + 40% USDC），Balancer 可以用**一次 swap**完成 rebalance，而 Uniswap 需要多次交易。

```
Uniswap 方式：                   Balancer 方式：
① 50% USDC → ETH               ① 一次 batchSwap 完成
② 50% USDC → DAI               {tokenIn: USDC, swaps: [
③ 手动调整比例                      {poolId: ETH/USDC, amount: 60%},
                                   {poolId: DAI/USDC, amount: 40%}
                                 ]}
```

### 3. Hyperliquid — 链上永续合约 DEX

#### 是什么

Hyperliquid 是一条**专为交易设计的 L1 区块链**，提供**链上永续合约（Perpetual Futures）**交易。与 Uniswap 的现货不同，Hyperliquid 允许用户做多/做空、使用杠杆。

#### 核心概念

| 概念 | 说明 | Agent 涉及风险 |
|------|------|--------------|
| **永续合约** | 没有到期日的期货合约，靠资金费率锚定现货价格 | 资金费率方向不对 → 持仓成本高 |
| **杠杆** | 最高 40x，放大收益和损失 | 高杠杆 + 清算 = 归零风险 |
| **保证金** | 跨仓/逐仓：跨仓共享保证金池，逐仓隔离风险 | 逐仓更适合 Agent（风险隔离） |
| **资金费率** | 多头付空头或空头付多头的定期费用 | Agent 需要监控费率方向 |
| **清算** | 保证金不足时强制平仓 | Agent 最大的风险——AI 延迟导致清算 |
| **市价/限价/TWAP/止损** | 四种订单类型 | Agent 需要用限价 + 止损组合 |

#### Agent 与 Hyperliquid 交互的风险

| 风险 | 为什么对 Agent 特别危险 | 缓解措施 |
|------|----------------------|---------|
| **清算延迟** | Agent 监控清理仓位的速度可能不够快 | 设置预警阈值（健康因子 > 2），提前减仓 |
| **资金费率亏损** | Agent 持仓过夜，资金费率方向持续不利 | 设置费率监控，方向不对时自动平仓 |
| **API 延迟** | Agent 通过 API 交易，网络延迟可能导致报价过期 | 限价单代替市价单 |
| **滑点放大** | 杠杆放大后的小滑点 = 大损失 | 严格滑点限制，低杠杆（≤3x） |
| **合约漏洞** | 链上合约被攻击 | 仅使用经审计的合约，设置最大损失上限 |

#### 为什么 DCA Agent 不直接使用

DCA Agent 是做**现货定投**（低风险，简单策略），永续合约需要在 Module E 的上下文中理解，但不建议直接扩展到 DCA 场景。如果要扩展，应该作为一个独立的 **Agent 交易策略**（如 Grid Trading 或 Delta Neutral）来设计，需要全新的权限策略和风险模型。

### 4. Lido — 流动性质押

#### 是什么

Lido 是最大的**流动性质押（Liquid Staking）**协议。用户将 ETH 存入 Lido → 获得 stETH → stETH 可以像 ETH 一样在 DeFi 中使用（同时每日累积质押收益）。

#### 核心机制

```
用户存入 ETH
     │
     ▼
┌──────────────────────────────┐
│  Lido 协议                     │
│  将 ETH 分配给节点运营商         │
│  节点运营商运行验证者并获得奖励    │
│  奖励分配给 stETH 持有者         │
└──────────────────────────────┘
     │
     ▼
用户获得 stETH
  └─ 每日自动累积质押收益
  └─ 可随时在二级市场卖出（Curve 等）
  └─ 可用作 DeFi 抵押品（Aave、MakerDAO）
```

#### 关键风险

| 风险 | 说明 | Agent 如何处理 |
|------|------|---------------|
| **脱锚风险** | stETH/ETH 汇率偏离 1:1（2022 年曾跌至 0.95） | 监控汇率偏差，偏差 > 阈值时暂停操作 |
| **节点运营商风险** | 节点被罚没（Slashing）→ stETH 价值下降 | Lido 有保险基金覆盖部分 slashing 损失 |
| **赎回延迟** | stETH → ETH 通过 Curve 兑换，深度可能不足 | 大额兑换前模拟执行，检查滑点 |
| **合约风险** | Lido 合约漏洞 | 合约白名单机制 |
| **收益波动** | 质押 APR 随全网质押率变化 | Agent 记录历史收益率供人类参考 |

#### DCA Agent 扩展场景：ETH 质押收益再投资

```
当前：USDC → ETH（swap）→ 持有

扩展：USDC → ETH（swap）→ 存入 Lido 获得 stETH
  └─ 质押收益自动复投
  └─ 比单纯持有多一层生息逻辑
```

### 5. Gitcoin — 公共物品资助

#### 是什么

Gitcoin 是一个**公共物品资助平台**，核心机制是**二次方融资（Quadratic Funding）**——社区捐赠 + 匹配池资金，小额捐赠获得更大匹配权重。

#### 核心机制

```
捐赠者 A 捐赠 1 DAI → 匹配池匹配 N DAI（N 取决于总捐赠人数）
捐赠者 B 捐赠 1 DAI → 匹配池匹配 N DAI
捐赠者 C 捐赠 100 DAI → 匹配池匹配 N/100 DAI

关键：捐赠人数比捐赠金额更重要
       1 个人捐 100 DAI < 100 个人各捐 1 DAI
```

#### Gitcoin 与 Agent 的关系

| 场景 | Agent 能做什么 | 风险 |
|------|--------------|------|
| **自动捐赠** | Agent 按预设策略（如每周匹配）自动捐赠 | 超出预算 |
| **项目筛选** | Agent 根据项目描述、GitHub 活动等自动筛选值得捐赠的项目 | 筛选偏见、被操纵 |
| **匹配计算** | Agent 计算每个项目的匹配权重，优化捐赠分配 | 公式误解 |
| **捐赠证明** | Agent 记录每次捐赠的 tx hash，生成捐赠报告 | 隐私暴露 |

#### 与 DCA Agent 的关系

Gitcoin 不是 DeFi 协议，而是**公共物品资助**。它与 DCA Agent 的关系在于——如果 Agent 的支付能力（x402 + Pact）扩展到**程序化捐赠**场景：

```
DCA Agent 能力移植到 Gitcoin：
  ① 用户设定：每周自动捐赠 50 USDC 到 Gitcoin 匹配池
  ② Agent 构造 Pact（预算 200 USDC/月，仅 Gitcoin 合约）
  ③ Agent 每周调用 Gitcoin 合约完成捐赠
  ④ 记录 tx hash 作为捐赠证明
```

这个场景需要纳入 Module G（Governance/Coordination）或作为总交付的扩展方案。

### 1. Prompt Injection（提示词注入）

#### 是什么

> "提示词注入是一种针对对话式 AI 的社会工程攻击。第三方（不是用户也不是 AI 本身）通过将恶意指令隐藏在对话上下文中来误导模型。"

OpenAI 定义。它不是"AI 犯错"，而是**攻击者利用 AI 的指令跟随能力**来操纵 Agent。

#### 攻击方式

| 攻击类型 | 如何实现 | 在 DCA Agent 中的影响 |
|---------|---------|---------------------|
| **直接注入** | 用户输入中包含恶意指令 | 如果用户本身是攻击者，可能绕过 Pact 边界（但 Cobo Policy Engine 强制执行，无法绕过） |
| **间接注入** | 恶意内容来自第三方——网页、文档、邮件、工具返回 | Agent 在读取 x402 响应时收到伪造的 PAYMENT-REQUIRED header → 误向攻击者付款 |
| **工具返回污染** | Agent 调用的 API 返回了被篡改的数据 | Uniswap Quoter 返回虚假报价 → Agent 接受不利价格 |

#### 在 DCA Agent 中的攻击场景模拟

```
攻击场景：x402 间接注入

① Agent 调用 x402 API Server 获取数据
② 攻击者控制了该服务端（或中间人攻击）
③ 服务端返回被污染的 PAYMENT-REQUIRED header：
    {
      "scheme": "exact",
      "price": "1000",              ← 正常价 0.001，被改成 1000
      "payTo": "0xAttackerAddress"  ← 收款地址改为攻击者
    }
④ Agent 解析 402 响应 → 检查 Pact 边界
     └─ 金额 1000 USDC > 单笔限额 200 USDC → ❌ Policy Engine 拒绝
     └─ 收款地址 0xAttacker ∉ 白名单 → ❌ 拒绝
⑤ Agent 记录：Pact 边界被触发，操作被拒绝
⑥ 不是 Agent "聪明"——是 Cobo Policy Engine 在基础设施层面拦截了
```

#### Cobo CAW 的防御能力分析

| 攻击入口 | Cobo Policy Engine 能否拦截 | 拦截机制 |
|---------|---------------------------|---------|
| Agent 收到 x402 虚假报价 | ✅ 能拦截（金额超 Pact 限额） | Policy Engine 检查单笔金额 ≤ 限额 |
| Agent 收到虚假收款地址 | ✅ 能拦截（地址不在白名单） | 地址白名单机制 |
| Agent 收到恶意 swap 参数 | ✅ 能拦截（合约地址不在白名单） | 合约白名单机制 |
| Agent 被诱导调非白名单合约 | ✅ 能拦截 | Policy Engine 的 contract allowlist |
| Agent 被诱导多次小额支付 | ⚠️ 部分拦截（累计上限会触发） | 累计预算上限 + 完成条件 |
| Agent 被诱导泄漏上下文信息 | ❌ **无法拦截**（Policy Engine 不检查 Agent 内部状态） | 需要 Agent 层面的上下文隔离 |

**关键结论：** Cobo CAW 的 Policy Engine 能拦截**所有涉及链上资产转移**的攻击，但**不能拦截 Agent 上下文中的信息泄露**。后者需要 Agent 本身的安全设计（指令层级、输入过滤、最小上下文）。

#### OpenAI 的防御策略（适用于 Agent 层面）

| 策略 | 说明 | DCA Agent 如何应用 |
|------|------|-------------------|
| **Instruction Hierarchy** | 模型区分可信/不可信指令——系统指令 > 用户指令 > 第三方内容 | Agent 应该区分：Pact 策略（最高级）> 用户参数（次级）> 外部返回数据（最低级） |
| **工具沙箱** | 代码执行工具在沙箱中运行，防止影响宿主系统 | x402 的付款参数在传递到 Cobo API 前应经过策略检查 |
| **用户确认** | 敏感操作前暂停并请求人类确认 | DCA Agent 的高风险操作已设计为人工确认（详见 Module D 执行策略） |
| **给具体指令** | 避免过于宽泛的指令——"检查所有邮件并做你需要做的事" | DCA Agent 的 Pact 已经是具体的：调哪个合约、花多少钱、多久一次 |

### 2. Sensitive Information Disclosure（敏感信息披露）

#### 是什么

OWASP LLM02:2025：LLM 可能在其输出中意外暴露**个人身份信息（PII）、财务数据、安全凭证、商业机密**等敏感信息。

#### 在 DCA Agent 中的风险

| 信息类型 | 存储位置 | 被泄露的方式 | 后果 |
|---------|---------|------------|------|
| **钱包地址** | Agent 上下文、日志、Cobo 审计日志 | Agent 在回复人类时打印了完整地址 | 链上地址公开，风险低 |
| **交易金额** | Agent 操作日志 | Agent 在对话中泄露了预算信息 | 隐私泄露，风险中 |
| **Cobo API Key** | Agent 环境变量 | Agent 被注入后输出环境变量 | ⚠️ **严重**——攻击者可滥用 API Key |
| **Pact 策略** | Agent 上下文、日志 | Agent 被注入后输出 Pact 细节 | 攻击者了解 Agent 的权限边界 |
| **人类对话内容** | Agent 上下文 | Agent 被注入后输出历史对话 | 隐私泄露 |

#### Cobo CAW 的防御能力

| 保护对象 | Cobo 层面 | Agent 层面 |
|---------|----------|-----------|
| API Key | API Key 绑定到特定 Pact，超出 Pact 范围的操作被拒绝 | 不应在对话中输出 |
| 钱包私钥 | Cobo MPC 托管，Agent 从不接触 | 不适用 |
| 交易权限 | Pact + Policy Engine 强制执行 | PAC 策略不应被 Agent 输出 |

#### 缓解措施

| 措施 | DCA Agent 中的实现 |
|------|-------------------|
| **最小数据暴露** | Agent 在回复人类时只展示 tx hash 的后几位，不暴露完整地址 |
| **上下文隔离** | 每次执行只加载必要的上下文，执行完毕后清除 |
| **日志脱敏** | Agent 日志中对 API Key、钱包地址等做脱敏处理 |
| **输入验证** | Agent 对 x402 响应中的参数做类型检查（防止注入） |
| **输出过滤** | Agent 在返回给人类的结果中过滤掉敏感信息 |

### 3. Excessive Agency（代理过剩）

#### 是什么

OWASP LLM06:2025：当 LLM Agent 被授予的**功能、权限或自主性超出了实际需要**时，就产生了代理过剩风险。

```
代理过剩 = 过多的功能 + 过多的权限 + 过多的自主性
```

#### 三个根因

| 根因 | 定义 | 在 DCA Agent 中的体现 |
|------|------|---------------------|
| **Excessive Functionality（功能过多）** | Agent 拥有不需要的工具/能力 | DCA Agent 只需要 Uniswap swap 和 x402 pay——不应有删除文件、改配置等其他能力 |
| **Excessive Permissions（权限过大）** | Agent 的权限超出了执行任务所需 | Pact 已经限制了——仅 Uniswap Router + x402 白名单地址 |
| **Excessive Autonomy（自主性过高）** | Agent 在高风险操作前不需要人类确认 | Module D 设计了人工确认阈值——超预算/非白名单/连续失败都需要人类介入 |

#### 在 DCA Agent 中的体现

##### 功能方面

```
DCA Agent 的能力列表：
  ├─ dca.plan（意图解析）      ✅ 必要
  ├─ pact.submit（Pact 构造）  ✅ 必要
  ├─ dex.quote（报价查询）      ✅ 必要
  ├─ swap.execute（交易执行）   ✅ 必要
  ├─ tx.verify（交易验证）      ✅ 必要
  ├─ x402.pay（自动支付）       ✅ 必要
  │
  └─ 未启用的功能：              ❌ 已禁止
       ├─ 删除文件/修改配置      → 不在 Pact 范围内
       ├─ 调用非白名单合约       → Policy Engine 拒绝
       └─ 修改 Pact 策略         → 只有人类能操作
```

##### 权限方面

```
DCA Agent 的权限范围：
  ├─ 可以调 Uniswap V3 Router    ✅ 最小权限
  ├─ 可以调 x402 白名单地址       ✅ 最小权限
  ├─ 可以查询 Cobo 交易记录       ✅ 最小权限（只读）
  │
  └─ 不可以：
       ├─ 修改 Pact               ❌ 架构禁止
       ├─ 创建新钱包              ❌ 不在能力范围内
       ├─ 转移地址外的 token       ❌ 被白名单限制
       └─ 无限额度调用 approve    ❌ 在 Cobo 层面管理
```

##### 自主性方面

```
DCA Agent 的自主性分级：
  ├─ L0（全自动）：报价查询、交易验证        ✅ 自动
  ├─ L1（边界内自动）：swap 执行、x402 付款  ✅ 自动（Policy Engine 保护）
  ├─ L2（暂停通知）：连续失败、链异常        ⚠️ Agent 暂停，通知人类
  ├─ L3（必须确认）：新 Pact、超预算操作     ❌ 人类必须审核
  └─ L4（不可自动）：Pact 修改、紧急撤销    ❌ 仅人类操作
```

#### 与 Cobo CAW 的关系

**Pact 的设计本身就是对抗 Excessive Agency 的机制：**

| Excessive Agency 根因 | Pact 怎么解决 |
|----------------------|-------------|
| 功能过多 | Agent 只持有当前 Pact 范围内的 API Key，不在范围内无法操作 |
| 权限过大 | Pact 的 Policies 定义了最小权限——仅特定合约、特定函数、有限金额 |
| 自主性过高 | 高风险操作会被 Policy Engine 拒绝，Agent 无法绕过人类决策 |

---

### 三项风险在 DCA Agent 中的防御总览

| 风险 | Agent 层面防御 | Cobo 基础设施层面防御 | 防御强度 |
|------|--------------|---------------------|---------|
| **Prompt Injection** | Instruction Hierarchy、输入验证、输出过滤 | Policy Engine 拦截越权链上操作 | 🛡️ 强（链上操作安全，上下文信息有风险） |
| **Sensitive Information Disclosure** | 日志脱敏、上下文隔离、最小数据暴露 | API Key 绑定 Pact，超出范围无效 | 🛡️ 中（Agent 上下文中的信息需人工管理） |
| **Excessive Agency** | 能力最小化、权限范围定义、自主性分级 | Pact 四要素限制 + Completion Conditions | 🛡️ 强（架构强制，不可绕过） |
